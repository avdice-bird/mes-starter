## 更新 CLAUDE.md 的约定（互测共性结论）

- 每个业务 Controller 方法必须 `@Permissions` 或 `@Public()` 二选一，扫描测试兜底
- 自我保护三件套：不能删除/停用自己、不能修改自己的角色、内置角色不可删改
- 无权限码的接口只能是"只操作自己"的认证类接口，且必须登记白名单

## 复核补记（第 5 节同轮复盘）

- 复查发现：上面第 1、3 条约定当时只写在文档里，扫描测试并没有对应的反向断言——攻击项 7 的防线实际不存在。已补：`permissions-scan.e2e-spec.ts` 新增"每个 Controller 方法必须 @Permissions / @Public（或登记在认证白名单）"断言；白名单按"文件名 方法名"逐接口登记（login/refresh/logout/me），不是整文件放行——auth 控制器将来新增业务接口忘写 @Permissions 时这里会红。
- 断言做了三项变异验证，全部必须红才算数：①删 `@Permissions('menu:delete')` → 红；②删白名单条目 logout → 红；③给 health 控制器加无声明接口 → 红。还原后全绿。
- 变异验证揪出断言自身的两个盲区，都已修：
  1. 最初用固定 300 字符窗口找装饰器，会把**下一个方法**的 `@Public` 算进本方法——变异③能红全靠换成"装饰器块到方法名为止"的单条正则；
  2. `@Get(':id')` 带路由参数时正则失配，**所有带参路由静默跳过检查**——最危险的盲区（基线竟然是绿的），补了路由参数消费后才真正全覆盖（22 个 handler）。
- 教训写进 CLAUDE.md 协作规则：声称"扫描测试兜底"的约定，必须真的有那条测试，且断言本身要过变异验证——"测试绿"不等于"断言在检查"，静默跳过的正则和没写一样。
