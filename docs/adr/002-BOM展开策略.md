# ADR-002：BOM 展开策略

- 日期：2026-09-22（第 19 节）
- 状态：已采纳
- 关联节次：第 17、19 节

> 注：权限变更生效策略的决策记录原编号也是 ADR-002（`002-权限变更生效策略.md`），本文件按任务卡编号沿用 002，实际以文件名为准。

## 背景

多级 BOM 展开是典型的图遍历。最直觉的实现是逐级查库：每到一个节点查它的 BOM。10 级 × 每级 10 子件 = 上千次查询（N+1）。SQLite 本地查询快，掩盖不了这个量级差异。

## 候选方案

1. **逐级递归查库**：实现最直白；每次展开 N 个节点 = N+1 次查询；受网络/连接池影响最大，数据库一慢全慢。
2. **一次查全部 + 内存建图（已采纳）**：`loadGraph()` 一条查询拉全部 ACTIVE BOM 及明细，`Map<materialId, node>` 建图后纯内存递归；查询次数与 BOM 规模无关（固定 3 次）；环检测/深度防御/多路径汇总都在内存做，好测好调。
3. **递归 CTE**：让数据库做递归，查询次数最少（1 次）；SQLite 支持 CTE，但调试困难、损耗/汇总等业务计算仍要回内存，且把业务逻辑塞进 SQL 违反本项目"Service 层业务"的分层约定。

## 决定

选方案 2。`BomExplodeService.loadGraph()`（1 条查询）+ `explodeFromBom()`（纯内存，单测 9 例不碰数据库）。

## 实测数字（200 物料 + 20 BOM × 10 明细，树接口 /boms/:id/tree）

| 方案 | SQL 查询次数 | 耗时 |
|---|---|---|
| 逐级递归查库（改前） | **12**（节点 11 + 1） | ~4 ms |
| 内存建图（改后） | **6 → 优化后 3** | ~4 ms |

小数据量耗时差距不明显，但查询次数从 O(N) 降到 O(1)——这是规模拉大时的本质区别（1 万节点的 BOM：逐级 1 万次 vs 3 次）。

改后剩余 3 次：`findUnique`(本 BOM 骨架) + `loadGraph`(全图) + `material.findMany`(全量物料)。全量物料在当前量级（几百）无压力；若将来上万，改为"按展开结果需要的 id 批量查"或加缓存。

## 代价与注意

- **内存占用**：全图一次性载入。当前 20 BOM × 10 明细毫无压力；数万节点时需评估（Node 堆内 Map 可扛数万-数十万节点，超出再议方案 3）。
- **新鲜度**：图是请求时快照，事务内一致。展开期间别人改 BOM 不影响本次结果——对"查看树"语义正确。
- **环检测在图上**：保存明细时的检测（`assertNoCycle`）同样基于内存图 + 临时叠加本 BOM，逻辑与展开共用一份图结构，两处行为一致。
- CLAUDE.md 已加约定：**树形/递归查询禁止逐级查库**，一律"一次查全 + 内存展开"。
