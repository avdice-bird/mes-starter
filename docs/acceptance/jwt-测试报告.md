## 二、边界用例手工实测（对照任务卡 03 的 11 条）

实测环境：dev 服务运行中（NestJS :3000 / Vite :5173），curl 直打接口 + 浏览器操作。

| # | 用例 | 期望 | 实测结果 | 判定 |
|---|---|---|---|---|
| 1 | 用户不存在 vs 密码错误 | 同一条消息，不区分 | 两者均 `{"code":1002,"message":"用户名或密码错误"}`（**当前**连续失败第 3 次起统一返回 1010，详见 auth.md） | ✅ |
| 2 | 连续 5 次密码错误 → 锁 15 分钟 | 锁定期正确密码也拒，消息带剩余时间 | 当时第 6 次起正确密码被拒；**当前**第 5 次失败当次即返回 423 `code=1009`：`"密码错误次数过多，账号已锁定，请 15 分钟后再试"` | ✅ |
| 3 | 禁用状态的用户登录 | 拒绝，"账号已禁用" | `{"code":1002,"message":"账号已禁用"}` | ✅ |
| 4 | 已登录用户被禁用 | 下一次请求 401 | 库中置 status=0 后，旧 token 访问 /me 立即 `{"code":1002,"message":"未登录或登录已过期"}`（JwtStrategy 每请求查库） | ✅ |
| 5 | access token 过期 | 前端自动 refresh 换新，用户无感 | 浏览器实测：篡改 localStorage 的 accessToken 后刷新页面，页面正常加载、refresh token 已轮换、/me 正常显示"管理员" | ✅ |
| 6 | refresh token 过期/伪造 | 跳登录页 | 接口层：`{"code":1002,"message":"refresh token 无效"}`；前端收到后跳 `/login?redirect=原路径` | ✅ |
| 7 | refresh 重放（用过再用） | 拒绝（旋转） | 第一次刷新成功出新对；同一旧 refresh 再用 → `{"code":1002,"message":"refresh token 无效"}` | ✅ |
| 8 | 登出后用旧 refresh | 拒绝 | 登出成功后再刷 → `{"code":1002,"message":"refresh token 无效"}` | ✅ |
| 9 | 任何响应体不出现 password | 无密码字段 | /me 响应 `"password"` 字串检索 false；登录响应 user 仅 id/username/name | ✅ |
| 10 | 登录 1 分钟内 20 次 | 第 21 次起 429 | 连发 21 次：前 20 次 401（用户不存在），第 21 次 **429**；窗口过后恢复 | ✅ |
| 11 | 用户名带空格/大小写 | trim，区分大小写 | `"  admin  "` 登录成功（trim）；`ADMIN` 与 `admin` 为不同用户（区分大小写） | ✅ |

## 四、结论

11/11 边界用例全部通过；自动化 3 层全绿。已知接受项（记录在 `docs/log/05.md` 判断表）：锁定计数并发窗口最多多试一次（SQLite 写串行兜底）；refresh 接口未单独限流（refresh 为 2^256 随机串，暴力枚举不可行，第 58 节部署时加网关限流）。
