# 权限变更何时生效 —— ADR-002

- 日期：2026-09-18（第 7 节）
- 状态：已采纳

## 背景

角色权限被修改、用户被重新分配角色、用户被禁用后，**已经登录、手里还握着 access token 的人**怎么办？两种做法：

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 每次请求查库 | 改完下一次请求立即生效；实现 10 行；不新鲜的数据为零 | 每个受保护接口多 1-2 个查询 |
| B. 缓存 + 版本号 | 快 | 要处理版本号失效、多实例同步、缓存击穿，复杂度翻倍 |

## 决策

**选 A：`PermissionsGuard` 每次请求实时查库取用户权限码**（用户 → 用户角色 → 角色权限）。

理由：
1. 本项目是单人课程项目，并发量小，1-2 个索引查询的开销可忽略；
2. "改完立即生效"不需要写任何失效逻辑——不会漏、不会忘；
3. 第 7 节用例 9（禁用用户立即生效）在 JwtStrategy 里本来就要查库，方案 A 让全系统行为一致。

## 影响

- 修改角色权限后，该角色用户的**下一次请求**即按新权限执行，无需重新登录（`test/rbac.e2e-spec.ts` 用例 2 已验证）；
- 以后如果性能不够（如报工高频接口），只对高频接口局部升级为方案 B，并在本 ADR 追加记录。
