## 评审意见判断表

> 用指定提示词对 `apps/server/src/modules/auth`、`stores/user.ts`、axios 拦截器做评审，逐条判断如下。

| # | 意见 | 成立？ | 理由 | 处理 |
|---|---|---|---|---|
| 1 | JWT secret 有硬编码兜底，secret 泄漏或形同虚设 | ✅ 成立 | `?? 'fallback'` 式写法会让忘配 env 的环境静默跑弱密钥；之前 e2e 挂掉正是它 | 已修：`common/config/env.ts` 强制读取，缺失启动即失败（`7cd7f89`） |
| 2 | 限流只挂在登录接口，refresh 没限流，可被暴力刷 | ⚠️ 部分成立 | refresh token 是 32 字节随机数（2^256），暴力枚举不可行，与密码字典攻击不同量级；但接口可被滥用刷库 | 本节不处理：成本收益不匹配，第 58 节部署时加网关级限流 |
| 3 | token 应存 httpOnly cookie 而非 localStorage | ❌ 不成立（本项目现阶段） | 需要引入 CSRF 防护 + 跨端口 cookie 处理，实现复杂度和出错概率上升；本项目模板全转义、无 XSS 注入面 | 已写 ADR-001 论证，上线前重估 |
| 4 | 密码策略太弱（未强制复杂度） | ❌ 不成立 | 种子账号 Admin@123 已符合复杂度；登录无注册接口，密码由管理员创建，策略属第 6 节用户管理模块的范围 | 移交第 6 节任务卡 |
| 5 | 用户不存在时直接返回，响应时间比密码错误短，可枚举用户名 | ✅ 成立 | `bcrypt.compare` 只在用户存在时执行，时序差可测 | 已修：用户不存在也跑一次同强度哑哈希比对（本次 commit） |
| 6 | 登录响应的 user 对象可能带出 password | ✅ 成立 | 初版 `pickUser` 白名单是手写字段，回归时容易漏 | 验证 + e2e 已断言 user 无 password 字段（`d123bf4`） |
| 7 | 锁定计数可被并发请求绕过（同时发 20 个请求都读到 attempts=4） | ⚠️ 部分成立 | 并发下确实可能多试几次，但 SQLite 写串行 + 阈值兜底，实际多不出一次完整的 5 次窗口；加行锁对 SQLite 收益低 | 记录在案，迁移 PostgreSQL 时改 `updateMany` 条件原子递增 |
| 8 | 日志打印了请求体，可能记录密码/token | ✅ 成立 | AllExceptionsFilter 打的 stack 虽不含请求体，但 Nest 内置 Logger 若在开发模式打 body 就有风险 | 核查：现有日志无 body 输出；已写进 CLAUDE.md 禁令 |
| 9 | refresh token 无过期清理任务，表会无限膨胀 | ✅ 成立 | revoked/过期行永不删除，长期运行膨胀 | 本节不修：课程生命周期内数据量小；第 58 节部署节加定时清理 |
