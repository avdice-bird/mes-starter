# ADR-003：工单状态机的事务边界与并发控制

- 日期：2026-10-09
- 状态：已采纳
- 关联节次：第 30-33 节

## 背景

工单状态变更不是单行更新：一次 `transition` = 改状态 + 写 log（第 34 节起还要生成 N 条工序任务）。两个风险：

1. **一致性**：状态改完、log/任务写一半失败 → 工单已 RELEASED 却缺记录或缺工序（"半成品状态"）。
2. **并发**：两个人同时点"开工"，都读到 RELEASED、都判合法、都写 IN_PROGRESS，log 冒出两条。

## 候选方案

### 状态机实现

1. 方案 A：Service 里 `if (status === 'RELEASED') ...` 链——直观，但 49 个格子散落成毛球，加状态必漏改。
2. 方案 B：状态模式（每状态一个类）——面向对象纯正，本课规模下类数量爆炸，收益低。
3. 方案 C（采纳）：**转换表常量** `{ 状态: { 动作: 目标 } }` + `transition()` 唯一入口，Service 查表不写 if。表即规格（与 `docs/state-machine/work-order.md` 对照测试锁定）。

### 并发控制

1. 方案 A：悲观锁（`SELECT ... FOR UPDATE`）——SQLite 无此语法，且业务上工单操作冲突率极低，锁表得不偿失。
2. 方案 B：队列串行化——引入消息设施，远超本课范围。
3. 方案 C（采纳）：**乐观锁**。事务内二次查表判合法性（1006），`updateMany WHERE id AND version` 原子提交，count=0 抛 1007。写失败率低时乐观锁代价最小。

### 事务边界

1. 方案 A：每个写操作独立事务——正是要消灭的半成品状态。
2. 方案 B（采纳）：**一次用户动作 = 一个事务**；事务内只做查表、条件更新、log/任务写入；事务外只放"只读前置校验"（如 release 前查 ACTIVE 路线，不涉及写）。
3. 方案 C：把前置校验也塞进事务——校验失败同样回滚，语义等价，但拉长事务持锁时间，无收益。

## 决定

- 状态机 = 转换表 + `transition()` 单入口；**状态变更必须走 transition()，禁止直接 update status**（已写入 CLAUDE.md）。
- 并发 = 乐观锁（`version` 条件更新），所有工单写路径（transition、adjustPlan）覆盖。
- 事务边界 = 一次动作一个交互式事务；**事务内所有写操作必须用 `tx` 客户端**。
- SQLite 并发写：`PRAGMA busy_timeout = 5000` + `journal_mode = WAL`（PrismaService 初始化时设置），写冲突排队而非报错。

## 后果

- 好处：49 格转换逻辑一张表可审；并发冲突有明确用户话术（1006 告诉用户当前状态与可做动作，1007 提示刷新）；第 34 节"下达生成工序任务"只需在 transition 的事务回调里追加循环写 `tx.workOrderTask.createMany`，一致性天然成立。
- 代价：多一次事务内读（二次查表）；乐观锁在真正高并发写同一条工单时失败率高——MES 车间场景按工单维度冲突率可忽略。
- 注意：**回滚测试的教训**（transaction.e2e-spec.ts）——测试替身若把操作路由到顶层 Prisma 客户端而非 `tx`，写操作会绕开事务连接各自提交，回滚形同虚设。评审新代码时：事务回调里出现 `this.prisma.xxx`（而不是 `tx.xxx`）即为红旗。
