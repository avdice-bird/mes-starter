## 实测数字（任务卡要求改前/改后对照）

测试数据：200 物料 + 20 BOM × 10 明细（受控实验：进程内直调 service，Prisma `log:['query']` 计数）。

| 方案 | SQL 查询次数 | 耗时 |
|---|---|---|
| 改前：逐级递归查库 | **12**（11 节点 + 根） | ~4 ms |
| 改后：`loadGraph` 一次查全 + 内存展开 | **6 → 3**（优化掉重复查本 BOM 与按 id 查物料） | ~4 ms |

- 小数据量耗时都是毫秒级——**但查询次数从 O(N) 降到 O(1)** 才是本质：1 万节点的 BOM 是 1 万次 vs 3 次。
- 改后 3 次 = 本 BOM 骨架 1 + 全图 1 + 物料全量 1。物料上万时改为按需批量查或缓存（ADR-002 代价段已写）。
- 脚本里第一版"查询计数"挂在测试进程的 Prisma client 上，而 tree() 在服务进程执行——计到 0 次。改成进程内直调 service 才计准。工具测错对象比不测还危险。

## 索引（EXPLAIN QUERY PLAN）

- `BomItem(bomId)`：migration 建，EXPLAIN 显示走 `BomItem_bomId_index` ✅
- `Bom(materialId, status)`：`@@index([materialId, status])` 复合索引 ✅（按物料取 ACTIVE 是最高频查询）
- `Material(code)` unique 自带索引 ✅
